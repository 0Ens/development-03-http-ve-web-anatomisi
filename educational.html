Temel Kavram

HTTP İsteği ve Yanıtı

Her API çağrısının altında iki sade metin mesajı yatar: bir istek ve bir yanıt. HTTP'nin sözleşmesi tam olarak bu iki mesajın biçimini ve olası değerlerini tanımlar. DevTools'ta gördüğün her satır bu yapının bir yansımasıdır.

→ İSTEK (Request) 
GET /v1/forecast?latitude=41.01
   &longitude=28.95
   &daily=temperature_2m_max
   &timezone=Europe/Istanbul HTTP/1.1
Host:   api.open-meteo.com
Accept: */*

(body yok — GET isteği)
← YANIT (Response) 
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: *

{
  "latitude": 41.0,
  "daily": {
    "time": ["2026-09-07"],
    "temperature_2m_max": [27.0]
  }
}

Bir isteğin dört bileşeni vardır — hepsini gerçek bir istekten okuyabiliriz:

GET Metot — kaynağa ne yapılacağı
/v1/forecast?latitude=41&longitude=29 Path + Query — hangi kaynak, hangi filtreler
Host: api.open-meteo.com Header — metadata; zorunlu ya da opsiyonel
(body yok) Body — GET'te boş; POST/PUT'ta veri taşır

Protokol Sözleşmesi

Status Code'lar

Yanıtın ilk satırındaki üç haneli sayı — status code — sunucunun isteği nasıl değerlendirdiğini söyler. Bu kodların aralıkları sözleşmenin bir parçasıdır; body'yi parse etmeden önce kodu kontrol etmek doğru tasarımdır.

200
OK
İstek başarılı; body veriyi içeriyor. Open-Meteo bu örnekte daily tahmin verisini döndürüyor.
400
Bad Request
Parametre hatalı ya da aralık dışı. Open-Meteo'nun body'si: {"reason":"Latitude must be in range..."}
404
Not Found
Kaynak mevcut değil. Geocoding API bilinmeyen şehirde 404 değil, 200 + boş results dizisi döner — body'yi kontrol etmek zorunlu.
◈

Status code yeterli değil. Geocoding API bilinmeyen şehir için 200 döndürüp results: [] veriyor. Bu yüzden scriptte status !== 200 kontrolüne ek olarak results.length da kontrol edilmesi gerekiyor. Sözleşmeyi okumadan bu detay gözden kaçardı.

Keşfedilen Endpoint'ler

API Sözleşmesi

Postman'de keşfedilen dört endpoint — her biri için metot, URL, parametreler ve gözlemlenen status code'lar. "Sözleşmeyi okuyan biri Postman'i açıp API'yi senin kadar iyi kullanabilmeli" hedefi bu dokümantasyonun ölçütü.

GET api.open-meteo.com/v1/forecast

7 günlük (veya 1–16 günlük) günlük hava tahmini. Scriptin ana endpoint'i. daily parametresiyle hangi değişkenlerin isteneceği seçilir.

ParametreZorunlu?Açıklama
latitude, longitudezorunluKoordinat (−90/90, −180/180)
dailyzorunluVirgülle ayrılmış değişkenler: temperature_2m_max, precipitation_sum, …
timezoneopsiyonelauto ya da Europe/Istanbul — tarihleri yerel saate göre hizalar
forecast_daysopsiyonel1–16, varsayılan 7

Gözlemlenen status: 200 OK · 400 Bad Request

GET api.open-meteo.com/v1/forecast ?current=…

Anlık hava durumu. daily yerine current parametresi kullanılır. Aynı endpoint, farklı parametre.

ParametreZorunlu?Açıklama
currentzorunlutemperature_2m, wind_speed_10m, weather_code, …

Gözlemlenen status: 200 OK

GET api.open-meteo.com/v1/archive

ERA5 reanaliz veritabanından 1940'a kadar giden tarihsel hava verisi. start_date / end_date zorunlu; bitiş tarihi en fazla dün olabilir.

ParametreZorunlu?Açıklama
start_date, end_datezorunluISO 8601 formatı: YYYY-MM-DD
dailyzorunluİstenen değişkenler

Gözlemlenen status: 200 OK · 400 Bad Request

GET geocoding-api.open-meteo.com/v1/search

Şehir adından koordinat ve zaman dilimi çözümleme. Script CLI argümanını (node src/index.js Tokyo) koordinata dönüştürmek için bu endpoint'i kullanır.

ParametreZorunlu?Açıklama
namezorunluŞehir adı — kısmi eşleşmeyi kabul eder
countopsiyonelSonuç adedi, varsayılan 10
languageopsiyonelen, tr, …
◈

Bulunamayan şehirde 200 OK + results: [] — 404 değil. Bu bir sözleşme detayıdır ve ancak Postman'de deneyerek anlaşılır.

Hata cevabı da sözleşmenin parçasıdır

Open-Meteo 400 döndürdüğünde body'sinde reason alanı bulunur — scriptteki toErrorMessage() bu alanı okuyarak kullanıcıya anlamlı mesaj gösterir.

400 Bad Request — response body 
{
  "reason": "Latitude must be in range of -90 to 90°. Given: 999.0.",
  "error": true
}

Kod Tasarımı

Modüler Mimari

Ödevin en kritik yapısal kısıtı: fetch katmanı ve dönüşüm fonksiyonları ayrı modüllerde. Bu ayrım kulağa basit gelir — ama test yazılabilirliği açısından belirleyicidir.

fetch.js
API ile konuşur. Ağa bağımlı. Dönüşüm bilmez.
fetchGeocode(city) fetchForecast(lat, lon) fetchCurrent(lat, lon) fetchArchive(lat, lon, …)
→ { status, ok, data }
transform.js
Saf fonksiyonlar. Ağ bilmez. Test edilebilir.
toErrorMessage(status) findHottestDay(daily) formatForecast(daily) formatTemp(celsius)
→ dönüşmüş veri
index.js
Yönetici. Hata kontrolü ve çıktı üretimi.
process.argv[2] process.exit(1) console.log()

transform.js içindeki fonksiyonlar — findHottestDay, formatTemp, toErrorMessage — sadece JavaScript değerleri alır ve döndürür. Hiçbirinde fetch çağrısı yok. Bu yüzden internet bağlantısı olmadan, kaydedilmiş bir JSON dosyasıyla test edilebilirler.

◈

Neden önemli: fetch ve dönüşüm birbirine karışsaydı testler ya ağa bağımlı olurdu (CI'da flakey, API kapalıyken kırık), ya da karmaşık mock altyapısı gerekirdi. Ayrım sadelik getirir: "ağa bağlı kod ağ olmadan test edilmez, dönüşüm kodu edilir."

Erken Çıkış Deseni

200 dışı bir yanıt geldiğinde — ya da geocoding sonuç döndürmediğinde — script stack trace atmadan temiz bir mesajla çıkar. Bu Unix CLI sözleşmesidir: başarı = exit 0, hata = exit 1.

src/index.js — hata yönetimi 
const { status, data } = await fetchForecast(lat, lon, tz);

if (status !== 200) {
  console.error(`Hata: ${toErrorMessage(status, data)}`);
  process.exit(1);  // stack trace yok — okunur mesaj, sonra çıkış
}

// buraya sadece 200 OK ile ulaşılır
const hottest = findHottestDay(data.daily);

Test Stratejisi

Fixture Tabanlı Unit Test

Testler gerçek API'ye çıkmaz. Bunun yerine, gerçek bir API cevabından kopyalanmış bir JSON dosyası — fixture — kullanılır. Bu sayede testler: internet yokken de çalışır, API kapalıyken de yeşildir, CI'da güvenilirdir.

◈

Fixture'ı kendin kopyala. Uydurma fixture, gerçek API'nin alan adlarını yanlış tahmin ettiğinde testler yeşil ama script kırık olur — bu "testlerin sana yalan söylemesi" durumudur ve hiç test olmaktan kötüdür. istanbul-forecast.json gerçek API cevabından kopyalandı.

Beklenen veri — en sıcak günü doğru bulur
findHottestDay(fixture.daily) → { date: "2026-09-12", maxTemp: 28.1 }
Boş liste — null döner
findHottestDay({ time: [], temperature_2m_max: [] }) → null
Eksik alan — null değerleri filtreler, null döner
findHottestDay({ time: ["…"], temperature_2m_max: [null, null] }) → null
200 dışı status → okunabilir hata mesajı (API reason ile)
toErrorMessage(400, { reason: "Latitude must be…" }) → "Geçersiz istek: Latitude…"
Tanımsız status kodu → kodu içeren genel mesaj
toErrorMessage(418) → "Beklenmeyen hata (HTTP 418)."
Terminal — npm test 
$ node --test tests/transform.test.js

Çıkarımlar

Ne Öğrendim

Sözleşme
HTTP sözleşmesini tüketici gözüyle okumak
Postman'de endpoint'leri keşfederken "bu parametre yoksa ne olur?" diye sormak, sadece 200 gören koddan çok daha sağlam bir anlayış veriyor. Birkaç kart sonra aynı sözleşmeyi yazan taraf olunacak.
Body
Hata cevabı da sözleşmenin parçasıdır
{"reason":"Latitude must be…"} yapısını bilmeden anlamlı hata mesajı üretmek mümkün değil. 400 ve 404'ün body'si de dokümante edilmeli.
Mimari
Ayrım test yazmayı mümkün kılar
transform.js saf fonksiyonlar içerdiği için ağa çıkmadan test edilebilir. fetch ve dönüşüm iç içe olsaydı testler ya ağa bağımlı olurdu ya da mock altyapısı isterdi.
Status
Status code tek başına yeterli değil
Geocoding API bilinmeyen şehir için 404 değil, 200 + boş results dönüyor. Sözleşmeyi okumadan bu detay atlanırdı ve script hatalı çalışırdı.
CLI
process.exit(1) temiz çıkış sağlar
Stack trace atmak yerine okunur hata mesajı basıp çıkmak, scripti gerçek bir araç gibi hissettiriyor. CI ortamında da doğru çıkış kodu üretiyor.
Fixture
Gerçek API cevabından fixture kopyalanır
Uydurma fixture, gerçek API'nin alan adlarını yanlış tahmin ederse testler yeşil ama script kırık olur. istanbul-forecast.json gerçek bir API cevabıdır.
